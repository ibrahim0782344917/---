- لا يجوز للمساعد الذكي نشر المحتوى أو تغيير السعر أو الرصيد أو حالة تعويض مالي دون تفويض وموافقة بشرية.

## 2. تدقيق الأمان: ملاحظات تحتاج تحقيقاً

- كل الجداول العامة الـ 21 التي أظهرها فحص pg_class لديها RLS مفعل.
- أربع جداول عامة ليس لها سياسات SELECT/INSERT مباشرة وقت الفحص: shitreed_admin_activity، shitreed_admin_staff، shitreed_profile_admin_audit، store_review_audit. هذا قد يكون عزلاً مقصوداً لا ثغرة، ويحتاج مراجعة طريقة الوصول الإدارية.
- Supabase Security Advisor أشار أيضاً إلى **تعطيل حماية كلمات المرور المسرّبة (Leaked Password Protection)**؛ تحتاج فحص توفرها ضمن الخطة الحالية وتفعيلها بعد تقييم أثرها على تسجيل الدخول، ولا ندّعي أنها مفعّلة. المرجع: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
- Supabase Security Advisor أعاد 22 تحذيراً عن دوال SECURITY DEFINER يمكن استدعاؤها من دور authenticated. **هذا لا يثبت استغلالاً أو تسريباً**؛ تُراجع كل دالة وتفويضاتها ومعرّف المستخدم والتحقق من ملكية الموارد والتسجيل. لا نسحب EXECUTE عشوائياً دون اختبار؛ قد يتسبب ذلك في قطع الطلبات والإدارة.
- Performance Advisor: 9 علاقات FK دون فهارس مقترحة، 7 فهارس غير مستخدمة، و2 تحذير من سياسات permissive متعددة؛ لا نحذف أي فهرس قبل قياس الأداء واختبار الاستعلامات.
- RLS لكل جدول جديد قبل تعريضه لـ REST. لا تضع service_role داخل Flutter أو في المتصفح. الإدارة على الخادم وفي RLS؛ إخفاء زر غير كافٍ.
- صور أضرار المنتجات وطلبات الاسترجاع معلومات خاصة؛ لا تعتمد روابط عامة للصور الحساسة في إصدار نهائي. خدمة رفع الملفات يجب فحص MIME والحجم، واستخدام تخزين خاص وروابط مؤقتة.
- مراجع الرسمية: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable ؛ https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy

## 4. الهندسة المقترحة للاستقرار والتوسع

1. **واجهة المستخدم:** Flutter Android (عميل الزبون)، Flutter Admin اختياري، موقع الويب متجاوب بتصميم StoreKing المرخّص كمصدر إلهام وتكييف آمن، وليس نقل أسرار أو إعادة بيع قالب.
2. **الخادم/DB:** واجهة API واحدة مع Supabase Auth، RLS، PostgreSQL ومخزن خاص للوسائط؛ كل طلب يمتلك owner/buyer/store scoping، مع rate limits وتدقيق.
3. **CMS والإعدادات:** جداول stores/branches، products/variants، content_posts/media، page_versions، design_versions، publish_history، approvals؛ نشر إصدارات محددة فقط وrollback آمن. Config قابل للاستهلاك من الهاتف مع ETag/cache وfallback.
4. **التجارة:** Checkout واحد خادمي يحسب السعر والكمية والخصم والضريبة إن وجدت والتوصيل 5,000 د.ع كحقول منفصلة ويحتفظ بلقطة المنتجات، مع idempotency وinventory transactions.
5. **الاسترجاع:** Returns/items/evidence/reviews/decision_audit، رسوم الرجوع الاختياري 5,000 د.ع **مشروطة**؛ التلف المثبت من المتجر بلا خصم، ولا إعطاء موظف صلاحية تعديل ledger أو الأموال بلا تفويض.
6. **الاجتماعي والدعم:** ملفات عامة منفصلة عن البيانات الخاصة، منشورات وتعليقات وحظر وتبليغ، حضور realtime قائم على الاتصال، رسائل خاصة لا تقرؤها الإدارة افتراضياً، وعملية Moderation محدودة.
7. **المحفظة:** ledger ائتمان داخلي ذريّة وقيد عكسي immutable، no cashout، موافقات وأثر محاسبي قبل تشغيل.
8. **AI:** API خادمي فقط، استعلامات محدودة ببيانات منشورة أو طلب صاحب الحساب بعد تفويض، Knowledge base ذات مصادر معتمدة، safe prompts، مراجعة بشرية، ميزانية وسقف استخدام؛ تعطيل فعلي حتى الموافقة على التكلفة والمفتاح.
9. **الفروع:** فرع واحد verified حالياً، أية فروع جديدة draft → review → publish؛ إحداثيات وإدارة خدمة ومخزون منفصلة بعد اعتمادها.
10. **الوسائط:** تخزين خاص/عام حسب النوع، فحص نوع وصيغ، حد حجم، مالك مرخص، سجل النشر، لا تنزيل TikTok/YouTube/Facebook لإعادة الرفع دون حقوق.

## 5. خطة المراحل السبع مع بوابات قبول قابلة للقياس

### المرحلة 1 — سلامة وأدلة وفصل
**المنجز:** فحص GitHub/Supabase/Railway/CI وأخذ snapshot من كود المتجر.  
**المتبقي قبل الإغلاق:** نسخة DB احتياطية قابلة للاسترجاع، بيئة Staging معزولة، خطة اختبار مستخدمين دون بيانات حقيقية، تقرير أسرار وRLS ودوال definer، اختبار تشغيل آخر SHA، التوثيق.  
**معيار الخروج:** restore rehearsal ناجح + لا كتابة على Production أثناء الاختبارات + موافقة مالك على خطة النشر.

### المرحلة 2 — أساس تقني ومصادقة
إصلاح فشل Flutter في آخر نسخة، اختبار تسجيل/استعادة/حذف/جلسات، Admin owner وRBAC ومراجعة Functions، API مُوحد وأخطاء، توثيق OpenAPI والتحقق من المفاتيح.  
**المعيار:** tests لكل role (anon, buyerA, buyerB, staff, owner) و CI أخضر وثبوت عدم ظهور بيانات أخرى.

### المرحلة 3 — منتجات وطلبات واسترجاع ورصيد
الكتالوج والمتغيرات والملفات، رفع جماعي CSV preview، سلة وcheckout خادم، 5,000 توصيل، عناوين، أمر دفع COD، حالات وتسليم وفواتير، 5,000 رجوع اختيارية، تعويض الكسر، دفتر ائتمان مالي، تقارير.  
**المعيار:** مشتري فعلي/تجريبي معزول يكمل COD ثم تسليم موثّق ثم إرجاع وتعويض، المبالغ والعمولات صحيحة، استرجاع ولا خصومات تلقائية على التلف.

### المرحلة 4 — ملفات عامة ومحتوى/فيديو/محادثات
إنشاء schema منفصل مع RLS لمنشورات وصور وفيديو وتعليقات وإعجاب ومتابعة وحظر/بلاغ ودعم ومراسلة، وتشغيل مصادر الفيديو باحترام الحقوق.  
**المعيار:** تفاعل متعدد حسابات مستقلة، إشراف يحترم خصوصية الرسائل، التحديث متزامن، وتخزين الملفات آمن.

### المرحلة 5 — لوحة إدارة ذات صلاحيات دقيقة
Dashboard حقيقي، إدارة زبائن موظفين، سجلات عمليات، موافقات، مراقبة، فروع وتوصيل، CMS، Media Library، تصميم بالإصدارات/معاينة/التراجع، إشعارات وتقارير.  
**المعيار:** كل وظيفة مدعومة بـ API وصلاحيات واختبارات ويُسجّل من عدل ماذا ولماذا؛ يمنع التعديل عند غياب الدور.

### المرحلة 6 — ذكاء اصطناعي خادمي بموافقة
بعد موافقة واضحة على المفتاح والتكلفة والخصوصية: مساعد الزبون ومساعد الإدارة، مصادر محتوى مُعتمدة، ملخصات ومسودات، تصعيد لموظف، حوكمة وحدود وتكلفة.  
**المعيار:** استعلامات مطابقة لبيانات حقيقية، لا وصول لطلب الغير، لا نشر أو تعديل أموال تلقائي، تتبع ميزانية وإيقاف فوري.

### المرحلة 7 — تحضير الإنتاج والنشر
E2E + أمن + أداء + ترخيص/سياسات + Play data safety + توقيع APK/AAB + تجربة أجهزة + Domain/HTTPS + rollback/backup/monitoring.  
**المعيار:** لا Critical/High غير معالج، موافقة تجارية وقانونية، APK/AAB صالحان، نشر إنتاج تدريجي بموافقة المالك.

## 6. حالات اختبار إلزامية

- زبون A لا يصل إلى عنوان/طلب/رصيد/محادثة زبون B؛ وموظف دعم لا يصل لمعلومات خارج مهمته.
- بحث المنتجات لا يعرض منتجاً مخفياً أو غير متوفر بصورة مضللة.
- خادم Checkout يعيد حساب **المجموع + رسوم التوصيل 5,000**، والزبون يرى الإجمالي النهائي قبل التأكيد؛ لا يثق بسعر/رسوم أرسلها العميل.
- تكرار زر تأكيد الطلب أو رد شبكة بطيء لا ينشئ طلبين؛ استرجاع المخزون عند الإلغاء آمن ذرياً.
- رصيد المتجر لا يصبح نقدياً ولا يمكن تعديله بأمر عميل أو التكرار، وكل تغيير يسجل قيداً لا يُمحى.
- خصم رسوم إرجاع المنتج السليم المشروط لا يُطبّق عند ثبوت ضرر من المتجر، وتعويض الكسر لا يتم بلا تسجيل قرار.
- رسائل المستخدمين لا تكون مفهرسة علناً ولا متاحة لكل Admin؛ تظهر للإشراف حدود البلاغ فقط.
- AI لا يصل إلى بيانات شخصية بلا تحقق أو يغيّر السعر/النشر/المال؛ لا يعمل قبل وضع Budget وAPI key خادمي.
- رفع ملف .exe أو مسار مزدوج، أو صورة تخفي محتوى تنفيذي، يُرفض؛ رفع فيديو يُراجع الملكية والتخزين.
- محرك Google Places العام لشتريد لا يظهر متاجر منافسة على خريطة فروع العاني.
- إزالة موظف من دوره تمنع الوصول مباشرة، وتظل حركة التغيير مسجلة.
- النسخ الاحتياطي يُستعاد فعلياً إلى بيئة منفصلة ولا يقتصر على نجاح عملية النسخ.
- Flutter اختبارات فتح/عودة/صغير الشاشة/الوضع الليلي RTL، Android 36 وAAB Release توقيع صحيح.

## 7. قرار الإطلاق الآن

**NO-GO للإطلاق التجاري العام.** السبب: لا Staging DB مستقلة، لا Backup DB مثبت، جدول الاسترجاع والمحتوى غائبان، رسم التوصيل لم يُثبت في معاملة Checkout الخادمية، التحقق الأمني لدوال SECURITY DEFINER لازم، والخدمات الاجتماعية وAI ليست مكتملة.  
**المسموح حالياً:** Staging read-only / Preview من GitHub + اختبارات محلية / إعدادات غير مدفوعة، دون نشر إنتاج أو تغيير بيانات مالية.

## 8. الخدمات والقرارات الخارجية

| الخدمة | حالة التفعيل والاعتماد المطلوب |
|---|---|
| Supabase Staging Branch | لا توجد؛ قد ترتّب كلفة، يلزم قبول تكلفة أو خادم DB اختبار مستقل |
| OpenAI API | غير مفعّل؛ يحتاج مفتاح خادم وميزانية موافق عليها وضبط خصوصية |
| Google Maps/Places | تظهر مكونات سابقة، لا تفعّل مدفوعات/فواتير جديدة دون موافقة؛ فرع العاني فقط |
| ملفات فيديو/تخزين | تحتاج حجم تخزين/سياسة حقوق ونسب للمصادر/تكلفة موافق عليها |
| الدفع الإلكتروني | **غير مطلوب حالياً**؛ COD فقط |
| اتصال/واتساب/بريد دعم | لا تُخترع أرقام أو حسابات؛ تُستكمل من الإدارة بعد التحقق |
| Google Play | يحتاج signing secrets وسياسات ونشر بعد الاختبارات والموافقة |
| تصاريح قانونية وسياسات | مراجعة شروط الإرجاع والضمان وحقوق المستهلك والجهة التجارية قبل الإطلاق |

## 9. الخطوة العملية التالية

1. لا نبدأ schema migrations أو تعميم AI قبل توثيق قاعدة النسخ الاحتياطي وعزل staging عن Supabase production.
2. نراجع سبب فشل Flutter customer الأخير من GitHub logs ونعالجه في فرع التطوير فقط، ثم نوثق نتائج Android الثلاثة.
3. نعالج مراجعة 22 دالة SECURITY DEFINER بالأذونات وتحقيق شروطها واختبارها في staging بعد العزل.
4. بعدها ننتقل إلى الcheckout الحقيقي + رسوم توصيل ثابتة من الخادم، ونطبق returns/content schema ومراجعات RLS على قاعدة منفصلة أولاً.
5. تنشر كل مرحلة مع CI، تقرير فيديو/واجهة، وقائمة قبول/رفض، ثم تظل main والإنتاج بلا تعديل حتى الموافقة.

**تمييز مهم:** هذا الملف هو سجل تنفيذ وخطة قبول، وليس شهادة إنجاز لميزات لم تُختبر.
