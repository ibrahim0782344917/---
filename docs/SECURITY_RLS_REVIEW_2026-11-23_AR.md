# شتريد — تقرير تدقيق الصلاحيات (اختبار فقط)

التاريخ: 2026-11-23
البيئة الوحيدة المعدّلة: `shitreed-test` (`tgvdwotbrnhcoykuxdpr`).
**ممنوع دمج هذا الفرع أو النشر أو تشغيل الدفع الحقيقي قبل اكتمال موافقات التصميم والاختبارات.**

## نتائج الإصلاح
- بدأ التدقيق مع 18 دالة `SECURITY DEFINER` قابلة للاستدعاء بواسطة `anon`. أصبحت **0** بعد `REVOKE EXECUTE FROM PUBLIC, anon` وإعادة منح الصلاحيات المقصودة.
- كانت 47 دالة `SECURITY DEFINER` متاحة لدور `authenticated`. أصبحت **39**: حُجب الوصول المباشر لدوال trigger/event-trigger ومساعدات حصص الخرائط والدوال الداخلية؛ وحُوّلت دالة فحص جاهزية checkout إلى `SECURITY INVOKER`.
- أبقينا الدوال التي يحتاجها المستخدم المسجل، مثل إنشاء الطلبات ومتابعة الطلبات وقنوات الدعم، بدل إيقاف وظائف التطبيق.
- الدوال الداخلية الخاصة بحصص Google Places وOSM متاحة للخادم `service_role` فقط؛ غير متاحة لزائر أو مستخدم عادي.
- الجدولان `private_legacy.contacts` و `private_legacy.review_queue` غير مكشوفين لـ `anon` أو `authenticated`.

## اختبارات ناجحة داخل معاملات ROLLBACK
1. الزائر يرى **0** من الطلبات، ومُنع مباشرة من استدعاء جهات اتصال المتاجر، ومراجعة المتاجر الإدارية، وحارس حصص الخرائط.
2. حساب الإدارة الأول اجتاز فحص `shitreed_is_admin()` واستدعاء لوحة الإدارة.
3. حساب التاجر لم يتمكن من الوصول إلى لوحة الإدارة أو عرض تفاصيل طلب إداري أو تغيير صلاحيات الطاقم أو اعتماد المتجر أو الموافقة على تعويض. سُمح له بقراءة جهات اتصال متجره فقط.
4. حساب الاختبار الثالث لم يتمكن من رؤية الطلبات أو جهات اتصال المتاجر.
5. محاولة وضع `shitreed_role=admin` في `user_metadata` أو حقول JWT المحاكاة لم تمنح التاجر امتيازات الإدارة؛ الصلاحيات تعتمد على `auth.users.raw_app_meta_data` أو حسابات الطاقم الموثوقة.
6. إنشاء طلب تجريبي من مستخدم مسجل بقي يعمل بعد تقييد دوال trigger: المنتجات 10,000 د.ع + الشحن 5,000 = **15,000 د.ع**، مع حدث تاريخ واحد وتعديل مخزون واحد. المعاملة أُلغيت؛ الطلبات الأصلية بقيت 5.

**تنبيه:** هذه اختبارات أدوار PostgreSQL ومحاكاة claim داخل قاعدة البيانات، وليست بديلاً عن اختبار JWT حقيقي أو تطبيق فعلي على Android.

## تحذيرات Supabase المتبقية — لا تُخفى
- **39** `authenticated_security_definer_function_executable`: هذه الدوال مكشوفة للمسجلين عبر RPC، وبعضها مطلوب للعمل؛ توجد فحوص `auth.uid()`، ملكية، أو `shitreed_admin_role()` داخل الدوال التي عاينّاها. لا يجوز إلغاء المنح دفعة واحدة أو تحويل الدوال كلها إلى `SECURITY INVOKER` لأن ذلك قد يكسر RLS والتطبيق. تحتاج مراجعة كل مسار استدعاء واختبارات JWT حقيقية، وربما إعادة هيكلة لبعض RPCs.
- **6** `rls_enabled_no_policy` مستوى INFO: جدولان خاصان بزبائن سابقين وأربعة جداول إدارة/تدقيق. هذه جداول مقصود منع الوصول المباشر إليها؛ وجود RLS بدون سياسة يعني المنع التلقائي لغير الأدوار المتجاوزة RLS. لا نضيف سياسة عامة فقط لإزالة التنبيه.
- **1** `auth_leaked_password_protection`: يحتاج تفعيله من **Supabase Dashboard → Auth settings** في مشروع الاختبار، حسب توفر الميزة بخطة Supabase؛ لا يوجد أمر اتصال مدعوم هنا لتبديل إعداد Auth هذا مباشرة. توثيق رسمي: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection

## خطوات قبل اعتماد الإصدار
1. تفعيل حماية كلمات المرور المسرّبة في مشروع الاختبار إن كانت متاحة، ثم إعادة تشغيل Security Advisor.
2. اختبار وصول زبون وتاجر وإدارة باستخدام JWTs حقيقية عبر التطبيق وPostgREST، خصوصًا الدوال ذات الصلاحيات المرتفعة.
3. مراجعة 39 دالة `SECURITY DEFINER` لتحديد بديل `SECURITY INVOKER` أو نقل المنطق الخادمي إلى مسارات مقيدة عند الحاجة.
4. مراجعة أمان Storage وخرائط Google وأذونات حذف الحساب والتعويض والمدفوعات.
5. الإنتاج و`main` وGoogle Play خارج نطاق هذا التغيير.
