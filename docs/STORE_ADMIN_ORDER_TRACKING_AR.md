# شتريد — تشغيل نظام مراجعة التجار والطلبات

آخر مراجعة: 14 نوفمبر 2026.

## ما تم تنفيذه
- مراجعة المحلات من حساب مشرف مصرح له فقط، مع سبب 20–1000 حرف وسجل تدقيق دائم public.store_review_audit.
- فحص الصلاحية يتم من بيانات auth.users.raw_app_meta_data.shitreed_role الموثوقة من الخادم. لا يعتمد على user_metadata التي يستطيع المستخدم تعديلها، ولا على زر في الواجهة.
- كل طلب يبقى pending حتى يراجعه المشرف؛ لا يوجد اعتماد تلقائي.
- تتبع حالة الطلب في public.order_status_history عند الإنشاء وتغيير الحالة.
- تفاصيل المنتجات والكميات والسعر وقت الشراء من public.order_items.
- RLS على سجل الطلبات؛ الزبون وصاحب المتجر يريان الطلبات المسموح بها فقط.

## تعيين المشرف الأول — بقرار صريح من مالك المشروع
**لا يوجد أي مشرف مُعيَّن تلقائياً.** يجب أن يكون المشرف شخصاً موثوقاً، وأن يتم التحقق من هوية حسابه.
الإجراء المفضل: استخدام Supabase Auth Admin API من بيئة آمنة على الخادم لحساب المستخدم ذي UUID معروف ومتحقق منه، وتعيين app_metadata.shitreed_role = admin مع الحفاظ على حقول app_metadata القائمة.

لا تستخدم user_metadata، ولا ترسل service_role أو secret إلى الهاتف أو GitHub العامة أو المحادثة. لا تُنشئ مفاتيح إدارة جديدة داخل Flutter.

يمكن لمالك قاعدة البيانات استخدام SQL Editor لإجراء محدود ومراجع **فقط بعد التأكد من UUID المشرف المقصود ومن موافقته**. لا تُنفذ هذا المثال بحساب مجهول:

    update auth.users
       set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb)
           || '{"shitreed_role":"admin"}'::jsonb
     where id = '<VERIFIED_ADMIN_UUID>'::uuid;

لإلغاء الصلاحية يمكن لمالك القاعدة إزالة shitreed_role من raw_app_meta_data لحساب المشرف المحدد. يجب مراقبة أي تعديل إداري والاحتفاظ بسجل مناسب.

## كيف تراجع متجراً؟
1. افتح تطبيق «شتريد تاجر» وسجل الدخول بحساب المشرف المصرّح له.
2. ستظهر أيقونة الإدارة فقط عندما يؤكد الخادم صلاحية الحساب.
3. افتح «مراجعة المحلات»، وافحص اسم المحل والعنوان ورقم التواصل.
4. **تحقق من ملكية المحل خارج التطبيق** بمستند أو مكالمة موثوقة؛ التطبيق لا يزوّد حالياً نظام إثبات ملكية مدمجاً.
5. اكتب سبب القرار وحدد أنك تحققت من الملكية قبل الموافقة. يحفظ الخادم القرار وسجله ولا يسمح للتاجر بتغيير حالة الاعتماد.
6. بعد الاعتماد تظهر المنتجات المنشورة في تطبيق الزبون ويمكن إنشاء طلبات COD.

## لماذا لا نقبل طلبات المحلات المعلّقة؟
لأن الدالة place_cash_order ترفض كل متجر ليس في حالة approved. هذا حاجز مقصود ولا يُعطّل.

## فحوصات قبل الإطلاق التجاري
- اختبار على حسابَي زبون وتاجر مستقلّين، وبحساب إدارة مفوّض.
- اختبار فشل الموافقة من تاجر ومن مستخدم مجهول.
- التأكد من أن مشرفاً يمكنه مراجعة متجر pending ثم يظهر في واجهة الزبون دون إعادة تثبيت.
- اختبار طلب واحد من متجر معتمد في Staging مع مطابقة المنتجات والكميات ومخزون ما قبل وبعد العملية وحالات الإلغاء.
- اختبار RLS للوصول إلى بيانات العنوان والهاتف والطلبات من حسابات مختلفة.
- مراجعة دوال SECURITY DEFINER المسموح تنفيذها عبر API؛ تحتاج تدقيق أمني دوري، وقد تظهر تحذيرات Supabase رغم التحقق الداخلي.
- تمكين حماية كلمات المرور المسرّبة من إعدادات Supabase Auth.
- استكمال سياسة خصوصية منشورة، حذف الحساب، إجراءات الدعم والنزاعات والتوصيل، إشعارات FCM، رسوم النقل والتحصيل، توقيع Android RELEASE ثابت، واختبار AAB على Google Play.

**الحالة:** لا تُعلن جاهزية البيع العام قبل موافقة الإدارة واختبار طلب حقيقي آمن وتحقق المتطلبات أعلاه.
