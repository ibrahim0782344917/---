# فحص النشر على هاتف Android وحماية النسخ — 19 نوفمبر 2026

## ما يمكن اختباره حالياً
- APK تجريبية من GitHub Actions على الفرع feature/alani-launch-hardening-20261119.
- تطبيق الزبون، تطبيق التاجر، تطبيق إدارة شتريد والعاني (Admin واحد).
- نجاح Flutter analyze وflutter test لا يثبت صحة الربط الحقيقي ولا أمان المبيعات.

## طريقة الاختبار من الهاتف
1. افتح https://github.com/ibrahim0782344917/---/actions ثم Run الخاص بفرع التطوير.
2. يجب أن تكون جميع المهام الثلاث PASS وأن تظهر ثلاثة Artifacts بأسماء Customer/Merchant/Unified Admin.
3. افتح الـ Artifact وحمّل ملف ZIP، وفكّه ثم ثبّت APK الاختبار على Android.
4. إذا رفض Android تثبيت الملف كترقية بسبب اختلاف توقيع Debug، لا تحذف التطبيق القديم قبل مراجعة بياناته المحلية. لا تحذف بيانات Supabase السحابية عن طريق إزالة التطبيق.
5. لا تستخدم حساب زبون حقيقي لإنشاء طلبات اختبار، ولا تستخدم تفاصيل بطاقة دفع حقيقية.

## قائمة اختبار الزبون
- فتح التطبيق وشاشة الترحيب والتنقل والرجوع.
- تسجيل الدخول وإنشاء حساب اختبار (فقط على قاعدة اختبار مستقلة).
- ملف المستخدم والاسم والخصوصية والعناوين ومعلومات الطلبات.
- صفحة السيد إبراهيم العاني تعرض المنتجات الحقيقية والفرع المعتمد فقط.
- العروض غير المفعلة لا تظهر على أنها عروض نشطة.
- السلة تعرض subtotal + ٥٬٠٠٠ د.ع تقديرياً؛ زر تأكيد الطلب يظل مغلقاً حتى اعتماد الهجرة.
- صفحة حذف الحساب في التطبيق ترسل طلباً قابلاً للمراجعة فقط بعد تفعيل GRANT/RLS.
- الروابط القانونية والسياسات قابلة للفتح على HTTPS.

## قائمة اختبار التاجر
- حساب التاجر يرى متاجره هو فقط (A)، ولا يرى متجر B.
- إضافة/تعديل منتج (في Staging فقط)، رفع الصورة، الإبلاغ عن رفض المدخلات.
- إدارة المخزون والطلبات والعروض المحددة المدة (تم تعطيل العروض إنتاجياً حتى اعتماد RLS).
- تغيير حالة طلب ضمن الانتقالات المسموحة فقط؛ التأكد من سجلات التدقيق.

## قائمة اختبار Admin
- إدارة شتريد والسيد إبراهيم العاني داخل APK واحد.
- دخول صاحب الإدارة يفتح الأقسام المخوّل بها فقط.
- المستخدم بدور دعم لا يمكنه تعديل الرصيد/الرتب أو قراءة بيانات خاصة خارج صلاحياته.
- معاينة CSV للزبائن السابقين تظل محلية دون استيراد للبيانات إلى GitHub.
- طلبات الاسترجاع والمقالات لا تكون فعالة حتى بناء الجداول على Staging والتحقق.

## الاستعادة الحقيقية (لم تنفذ بعد)
1. راجع إعداد النسخ الاحتياطية من Dashboard مشروع Supabase شتريد.
2. أنشئ نسخة قاعدة بيانات Production بصورة آمنة، من دون وضع كلمات مرور أو بيانات في GitHub.
3. استرجع النسخة داخل مشروع Staging **منفصل ومقيّد الوصول**؛ لا تسترجع في الإنتاج.
4. تحقق من عدد السجلات، فحوص RLS، عدم كشف الهاتف والعنوان، وصحة الحفظ.
5. لا تفعّل API المدفوعة أو المدفوعات أو معالجة الرصيد قبل موافقة المالك.

## اختبارات SQL المنفصلة التي أصبحت آلية
- ٥٬٠٠٠ د.ع توصيل العاني فقط، منع طلب دون مخزون/طلب غير مصرح.
- استرجاع مع حالات انتقال وحقوق زبون، ووسائط مقال/فيديو منشورة وخصوصية المسودات.
- دفتر رصيد داخلي غير نقدي يدعم idempotency ويمنع التغيير والرصيد السالب.
- طلب حذف الحساب من مستخدمه فقط، ورسائل دعم خاصة بالمشترِ والتاجر.
- pg_dump + pg_restore على بيانات اختبار وهمية، **ولا يعني ذلك وجود نسخة إنتاج احتياطية**.

## معايير GO / NO-GO
- NO-GO: بدون نسخة استرجاع حقيقية، Staging Supabase، اختبار عملية طلب وإرجاع، واعتماد مفتاح AAB.
- GO للاختبارات المحلية فقط بعد نجاح Flutter APK artifacts.
- GO للنشر العام لا يُمنح إلا بعد اختبار APK على جهاز فعلي ومراجعة سياسة الخصوصية والـ Play Data safety والتوقيع.

## ما نحتاجه من مالك المشروع
- تحديد دومين رسمي مستقل لمتجر السيد إبراهيم العاني (Railway الحالية فيها دومين Staging فقط).
- إعداد Secrets للتوقيع داخل GitHub بنفسه، ولا يشاركها في أي محادثة.
- الموافقة على تكلفة Supabase Development Branch إن وُجدت، أو توفير قاعدة اختبار مستقلة.
- التأكيد النهائي للعنوان الرسمي ورقم الاتصال والشعار والحقوق القانونية للمحتوى.
