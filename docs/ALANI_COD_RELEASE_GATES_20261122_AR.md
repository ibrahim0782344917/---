# تشغيل طلبات السيد إبراهيم العاني — بوابة ما قبل الإنتاج 2026-11-22

## الوضع الحالي
- تم إعداد مسار خاص للطلب النقدي `place_alani_cash_order` ورسوم توصيل ثابتة ٥٬٠٠٠ دينار للطلب، وليس لكل منتج.
- مسار الطلب العام القديم يمنع إنشاء طلبات العاني دون موافقة الزبون على الرسوم، ويُبقي طلبات التجار الآخرين كما كانت.
- القاعدة الإنتاجية **لم تُعدّل** حتى الآن: لا حقل رسوم توصيل ولا وظيفة طلب العاني الجديدة. لا تقم بتشغيل علم checkout في الموقع أو APK قبل الترحيل والاختبار.
- واجهات الزبون والموقع أصبحت تستخدم الوظيفة الجديدة عند تفعيلها في البناء والإعدادات. قيمة المبلغ الموافق عليه تُراجع ذرياً قبل تسجيل الطلب وخصم المخزون.
- موقع Railway Staging الحالي يستخدم نفس قاعدة Supabase الحقيقية؛ **ليس قاعدة اختبار منفصلة**.
- كان في المتجر ٥ طلبات تاريخية عند الفحص؛ يجب أن تبقى مبالغها الأصلية دون زيادة.

## نتائج الاختبارات على PostgreSQL مستقل ببيانات تركيبية
- فاتورة زيت ٢٠٬٠٠٠ + عسل (٥٬٠٠٠ × ٢) + توصيل ٥٬٠٠٠ = ٣٥٬٠٠٠ د.ع.
- مخزون كل صنف يُنقص مرة واحدة فقط، وتُحفظ صورة أسعار كل سطر طلب.
- إرسال نفس requestKey يعيد الطلب ذاته دون رسوم أو خصم مخزون إضافيين.
- تغيّر إجمالي السلة أو نفاد المخزون يرفض العملية كلها ويرجع كل التعديلات.
- طلب العاني عبر المسار القديم يُرفض بدلاً من تقديم مبلغ لا يتضمن التوصيل.
- طلب متجر آخر يحتفظ بطريقة حسابه السابقة ورسوم توصيل ٠ في هذه التهيئة.
- الطلبات السابقة يبقى total_iqd كما كان، مع delivery_fee_iqd افتراضياً ٠.

## خطوات قبول إصدار استقبال الطلبات الحقيقي
1. إنشاء نسخة احتياطية كاملة وخاصة من قاعدة الإنتاج، تشمل بيانات الزبائن والطلبات والمخزون والدوال، والتحقق من القدرة على استرجاعها في قاعدة منفصلة؛ لا تحفظ نسخة شخصية في GitHub.
2. فحص تاريخ آخر ترحيل وتطابق تعريفات الدوال الأصلية مع التي بني عليها SQL الجديد، والتأكد من عدم إضافة تغييرات موازية.
3. تطبيق ملف `docs/ALANI_COD_VERIFIED_5000IQD_20261122.sql` كترحيل واحد بعد النسخة الاحتياطية.
4. التحقق في قاعدة الإنتاج: وجود delivery_fee_iqd، الدالة الجديدة، الصلاحيات `EXECUTE authenticated` فقط، وعدم تغيير الطلبات القديمة؛ لا تُنشئ طلبات اختبار بأسماء زبائن حقيقيين.
5. تجهيز قاعدة اختبار مستقلة أو آلية اختبارات معزولة، ومراجعة سياسة الاسترجاع وحالات الإلغاء والتوصيل على الأجهزة.
6. نشر الموقع والإدارة من الكود المُراجع ورفع APK تجريبي موصول بالخدمة، ثم تفعيل checkout على Railway فقط بعد مطابقة النسخة وخطة الرجوع.
7. تمكين ALANI_CHECKOUT_ENABLED=true وALANI_DELIVERY_TOTALS_VERIFIED=true في **بيئة معتمدة فقط**. لا تستخدمهما إذا لم يتحقق أي شرط سابق.
8. بناء نسخة Android بالعلمَين نفسيهما بعد نجاح اختبار الخادم؛ البناء العادي وAAB الحالي يبقيان مقفلين افتراضياً.
9. تجربة واحدة بموافقة المالك عبر حساب اختبار منفصل، والتحقق من سجل الطلب/المخزون/الإلغاء، ثم مراجعة قابلية الفتح للجمهور.

## إيقاف سريع وآمن بدون حذف بيانات
- أوقف علم ALANI_CHECKOUT_ENABLED على الموقع وأعد النشر حتى يتوقف استقبال الطلبات الجديدة.
- لمنع استخدام أي نسخة Android منشورة أو مسار API قديم مباشرة: أوقف صلاحية `EXECUTE` للدالة الجديدة عن authenticated بعد مراجعة فريق التشغيل:
  `REVOKE EXECUTE ON FUNCTION public.place_alani_cash_order(jsonb,text,text,text,uuid,bigint) FROM authenticated;`
- اترك مسار الطلب العام يرفض طلبات العاني مؤقتاً؛ هذا أفضل من السماح بطلب دون أجور التوصيل.
- لا تحذف حقل delivery_fee_iqd أو دالة checkout ما دامت هناك طلبات جديدة تعتمد عليهما.

## حدود هذا التغيير
- الدفع نقداً عند الاستلام فقط؛ لا زين كاش أو Visa أو Mastercard.
- إدخال التوصيل ٥٬٠٠٠ على الطلبات الجديدة؛ لا يوجد تتبع سائق أو رسوم مناطق أو نظام إرجاع مكتمل بعد.
- أنشأ المالك نسخة `pg_dump` مشفّرة على هاتف Android في 22 نوفمبر 2026، وظهر فحص أرشيف `pg_restore --list` ناجحاً، ونُسخت إلى Downloads؛ **لم يصل تأكيد اختبار استرجاع قاعدة البيانات المستقلة بعد**. لذلك **الإنتاج لم يُفعَّل**. لا يتضمن `pg_dump` ملفات Supabase Storage أو إعدادات المنصة.
